## What moved it from 302 to 0

1. **Retail passes positions and colours as nested temporaries.** The
   `Vec2f`s from `func_002b2970` and the `FclDrawColor`s from
   `func_002b2a60` are not named locals. They are struct-return temporaries
   written inside the consuming call:
   - `func_002e0620(h, func_002b2970(..), func_002b2970(..), ...)` with
     `Vec2f` parameters;
   - `*(FclDrawColor *)((u8 *)func_002e04e0(h) + 0x79) = func_002b2a60(..)`;
   - `func_002cacd0(func_002b2970(..), 1.0f, func_002b2a60(..), ...,
     func_00106a90(..), ..., func_0046a770(..), func_0046a770(..), 0xAA)`.

   b210 evaluates the struct-returning arguments first and computes the
   handle address before them. This fixed the loop-tail handle recompute and
   the `func_002cacd0` call order.
2. **Frame layout rule.** b210 places named non-array locals first, then
   temporaries in creation order, then arrays larger than 8 bytes. Arrays go
   in declaration order, earlier ones higher in the frame. Retail's three
   late 8-byte slots (0x160/0x158/0x150, the second position copy of each
   DCC/DD0 pair) are one `Vec2f spP[3]`, declared before `spD0`/`spC0`.
   Before that change the whole temporary region was shifted by 0x18
   (312 rows).
3. `(u8)` float results stored straight into their field
   (`*(u8 *)(work + i + 0xF6A) = (u8) func_002b2aa0(..)`) make b210 compute
   the store address before the call, as retail does.
4. **Loop rotation fixed.** Writing `for (var_19 = 0; (s16)var_19 < 2; ...)`
   keeps retail's `b cond` entry. The init coalesces with the function-level
   zero.
5. Temps that m2c split out of a single use were nested back into the next
   statement. The exception is the `u8 temp_3_flag` for
   `func_00110810(.., flag | 1)`, which must stay a temp.
6. `func_00106a90(..) <= func_002e7a60()` (not `e7a60() >= a90()`) gives
   retail's evaluation order. One `tbl = D_0063F688` had been placed inside
   an `if`.
7. **The F18 CSE fix.** In states 0x33/0x34 the index is assigned inside the
   first subscript:

   ```c
   if (func_002e26f0(F18[t = work[0x11]]) > D_00748908[t]) {
       if (func_002e26f0(F18[t]) > 5) ...
   ```

   Here `t` is `s32`. b210 then does not CSE the third F18 address, which
   matches retail.
8. `(s8)(s32)` on the `work[0x11]` argument of `func_002d8a60` and
   `func_002d4760` reproduces retail's argument order with the real `s8`
   parameters. `func_00106620((s16) t, 0)` works with its `(s32, s32)`
   declaration.

## Prototype conflicts (why this is not a MATCH)

The measurement script maps a `_VV` suffix back to the real symbol. The
compiled instructions are identical, only the relocation names differ. The
body needs three such aliases:

1. **`func_002e0620(void *, Vec2f, Vec2f, s32, s32, s16)`, 75 sites.** This
   is legitimate as a file-wide change, since the ABI passes the two 8-byte
   structs in `$a1`/`$a2`. But every other caller in the file passes
   `*(u64 *)&sp`: roughly 70 matched sites and a number of `NON_MATCHING`
   guarded bodies. All of them have to be rewritten to pass the `Vec2f`, and
   every matched function re-verified. This has not been done.
2. **`func_00106600` needs an `s16` parameter at 4 sites** (states 0x25 and
   0x2E). There, retail keeps the id raw in `$s3` from `func_002e2830`, then
   re-extends it before each `func_00106600`, `func_00106a90` and
   `func_00106620` call. An explicit `(s16)` cast is CSE'd into one saved
   extension. An `s16` temp is extended at its assignment, while retail's
   is raw. But matched `func_002dd3b0` passes its already-extended `s32 id`
   raw to `func_00106600`, which needs the current `s32` parameter.
   Switching the file to `s16` breaks dd3b0. Retyping dd3b0's `id` as `s16`
   costs 1173 edits there. The real definition in `g_data.c` takes `s16`.
3. **`func_00106cd0` returning `s16` at one site**
   (`func_00106a90(func_00106cd0(..))`, passed raw). The seven state-0xA
   `func_00106880(func_00106cd0(..))` sites need the file's current `s32`
   return, because an `s16` return is extended before an int parameter.
   `func_00106880` must stay `s32` for matched func_002df020, which passes
   its raw `s32 arg1`.

Items 2 and 3 are contradictions under the current model of b210's
extension rules: one prototype per callee cannot satisfy both this body and
the matched siblings. Resolving them needs either a better model of when
b210 elides or re-extends `s16` conversions, or a joint re-typing of
dd3b0/df020 that keeps them matching.
