# Action framing: func_001be050

This recovery emits 2164 executable bytes in the 2176-byte Persona 4 retail
window. Every code relocation is applied before the comparison; all executable
bytes are identical and the remaining twelve bytes are zero alignment. The
function is ordinary C and introduces no new compiler-owned data.

The starting evidence is the complete Persona 4 assembly, the IDA and Ghidra
bodies, and Persona 3 FES `func_002a4c70` from donor commit `04d95e2`. That donor
is itself NONMATCHING: it supplies structure and types, not an inherited match.

## Reconstructed state and Persona 4 behavior

The function uses two complete 28-byte position/quaternion poses, a 40-byte
interpolation cache, an intermediate quaternion, four three-component vectors
and a two-component horizontal vector. These are ordinary local objects;
there is no padded decompiler stack overlay or read beyond a three-float vector.

Several Persona 4 differences are material. The remembered camera distance is
raised to the desired distance when necessary. The direction is normalized
relative to the unit center before being positioned relative to the near point.
The alternative look-at uses a quarter of the vertical distance above the
unit's middle height. If that alternative succeeds, its quaternion is copied
directly; otherwise interpolation divides by the original angle, not the
angle returned by the alternative query. The five mode exceptions, 550-unit
minimum distance, 100-unit height limits, and 1.75 duration cap are
preserved in their retail order.

All float comparisons retain the observed ordered or negated-ordered forms.
Both endpoints are initialized before interpolation and before the final
camera submission. The cache flag protects the scalar's polynomial path.
The callback assumes the initialized camera, action and unit state that retail
dereferences; it does not add artificial defaults for missing battle records.

## Final compiler differences

The first typed reconstruction already emitted the correct 2164 bytes. Its
33 resolved differing words consisted of a two-register float allocation and
one multiplication operand order; the alignment tool showed 24 edits because
it does not decode every EE accumulator instruction.

Declaring the middle-height local immediately before the radius local assigns
their real, overlapping lifetimes as in retail, leaving one word. Separating
the measured vector length from its scale multiplication removes that last
operand-order difference:

```c
halfDistance = RwV3dLength(&delta);
halfDistance *= fGpffff8140;
```

Both assignments contribute to the actual distance calculation. No dummy
local, new optimization pragma, assembly, volatile access or instruction
padding is used. The canonical vector-length and normalization declarations
agree with the recovered providers.

`void (u8 *, f32, f32)` interface and explicitly converts its camera object
pointer. Its entire object, including all 46 functions and allocated data,
remains unchanged. The existing three action-camera recoveries also retain

unchanged by this additional promotion.
