## What the residual is

Registers in the second loop, retail against b210:

| Value          | Retail | b210 |
|----------------|--------|------|
| counter        | `$s0`  | `$s3` |
| `(s16)` copy   | `$s3`  | `$s0` |
| `a`            | `$s5`  | `$s5` |
| `on` / `off`   | `$s1` / `$s2` | `$s1` / `$s2` |

Changing declarations only rotates the named variables. The compiler's
sign-extension copy always takes `$s0`:

- `s16 k; s16 a;` gives counter `$s5`, `a` `$s3`, copy `$s0`.

The copy only leaves `$s0` when the loop counter is the parameter `arg1`
(whose home is `$s0`). With `for (arg1 = 0; (s16)arg1 < 2; arg1 = (s16)(arg1
+ 1)) { k = arg1; ... }` and an `s32 arg1`:

- the counter is `$s0`, as in retail;
- the copy `k` now outranks `on`/`off` (`$s1` against retail's `$s3`);
- the result is 22 words.

## Idea not yet tried

The b210 colouring order seems to be: sign-extension temps first, then named
locals (later declaration takes the lower register), then the counter. Retail
behaves as if the counter were the temp. A loop whose counter is a genuine
compiler temporary might produce this. Examples are a `while` over a pointer
or a count derived from an expression, with `k` as a named local declared
after `on`/`off`.
