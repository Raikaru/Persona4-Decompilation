# Prototype mismatch survey: func_00477c40 / func_00478140 (2026-09-26)

Question: does retail prove that one group of callers was compiled against a
different prototype than the definition (for example a stale header)? If so,
the mismatch is reproduced at module granularity with a waived H011
declaration. If the evidence is scattered or does not hold, nothing lands.

## Compiler facts used (MWCC b210, measured in this survey)

- A u16 value that is widened to an int-width parameter gets `andi 0xffff`,
  even from a u16 local. Example: a u16 local in func_00230d30 passed to an
  s32 parameter.
- An int value that is narrowed to a u16 parameter gets `andi`, unless it is
  a constant or a fresh `lhu` load. Example: an s32 local in func_00230d30.
- A u16 local passed to a u16 parameter goes through unmasked.
- A u16 argument to an unprototyped or `()` callee gets `andi`, because of
  default promotion.
- A callee masks its u16 parameters when it uses them. The masks on entry in
  both definitions therefore do not show the parameter type: func_00477c40
  matches as (u32,u32,u32), (u32,u16,u32), (u16,u16,u32) and (u16,u16,u16).

So "passed raw" means the caller's value and the parameter are the same class.
Constants and `lhu` loads are neutral.

### Definition side: the type is int-width

1. func_00478140 forwards `type` ($s3) raw to func_0047d110, func_004779b0
   and func_0047d0e0 (retail 0x004781B0-0x00478220).
2. func_0047ac90 forwards its `type` ($s5) raw to func_00477c40 and to the
   same three helpers (0x0047ACC4-0x0047AD48).
3. func_00477c40's type is int-width, from mdlSE func_0047df40 (survey A).
4. The helpers have one signature each. Suppose their type were u16: then
   func_0047ac90's type would be u16, and it could not reach func_00477c40
   raw. So the helpers' type is int-width, and so is func_00478140's
   (steps 1 and 2).

This holds whether or not the helpers are prototyped.

### Caller side: the Kosaka field code saw a u16 type

- func_00162680 has 0 words only with a u16 type.
- func_0015e960 passes a CSE'd u16 type raw.
- K_Cmd_CREATE_MDL and func_001658b0 match as written, or naturally, only
  with u16.

These callers sit in 0x0015e960-0x00177e20 (k_fldFBN, the field party cache in
code1_0016, k_fldUnit, k_command), all Kosaka field code. No caller there
requires an int-width type. No caller outside it requires a u16 type: the
effect, event and Fcl callers pass constants or `lhu` for the type. The
definition itself does require an int-width type.

**Decision B: YES, for the type parameter.** Kosaka field was compiled against
`func_00478140(u16 type, u16 id, u32 flags)`. The id is u16 in this prototype
because of field evidence (func_00162680, func_001658b0). On the definition
side the id is int-width only through the same unprototyped helper plumbing
as in A, so the id is not claimed as part of the proven mismatch.

## What landed

- New module header `include/Kosaka/k_model_internal.h`: the one field
  prototype, `extern void *func_00478140(u16 type, u16 id, u32 flags);`,
  with the evidence comment and `lint: allow H011 -- ...` directly above it.
  It is included by:
  - code1_0016.c
  - k_fldUnit.c
  - k_fldFBN.c
  - k_command_internal.h
  These files lose their own declarations: the u32 one in code1_0016.c and
  k_fldUnit.c, the s32-returning u16 one in k_fldFBN.c, and the Model* one in
  k_command_internal.h.
- The definition and mdlManager.c are unchanged.
- func_00162680 is installed (MATCH). This replaces its NON_MATCHING guard and
  stale notes.
- func_001658b0 passes its u16 `code` directly. The u32 `modelCode` copy is
  removed, and the function is still MATCH.
- config/symbols_recovered.txt gains `iGpffff9f10 = 0x00763000`
  (gp 0x7690F0 - 0x60F0). func_00162680's `mdlSetColor(obj, &iGpffff9f10)`
  needs this symbol to keep code1_0016.c link-eligible. Without it the link
  count drops to 593. Only this line was added; a full recover_symbols.py
  run also reshuffles unrelated entries.
- func_0015e960 is banked, not installed. The draft needs file-scope
  declarations that disagree with the rest of k_fldFBN.c (FBN_ENTRY is
  defined after it, and func_00477e80/func_0015d2c0/... use other
  spellings). Its remaining 71 words are the register colouring recorded in
  FldFBN_0015e960_20260926_body.c. The prototype it needs is now the module
  prototype.

The non-field declarations stay unchanged and keep their existing H011:
evtScript.c, effModel.c and effHelper.c `(u16, u16, s32)`, and y_fclModel.c
`(s32, u16, s32)`. Survey B suggests `(u32 type, u16 id, u32 flags)` for them
once mdlManager's id plumbing is recovered. A u32 id breaks effModel's
func_004abd80.
