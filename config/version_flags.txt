# Extra compile flags per compiler version key (see config/compiler_units.txt):
# `<version key> <flag> [flag ...]`, appended by tools/verify.py::unit_compile_flags
# in both verify and build.
#
# The b119 units reconstruct the RenderWare 3.7.0.2 block (core/plcore, core,
# pipe/p2, world) and are compiled against the vendored RenderWare headers in
# include/rw: `-nosyspath` makes MWCC find the <stdlib.h>-style includes in
# include/rw/std (the libc shims the headers need, no libc is otherwise
# available), include/rw/ps2 supplies the PlayStation 2 ostypes.h, and the
# remaining directories mirror the RenderWare source tree's include paths.
# `-O4`: the block was built at -O4 (plus `,p` per config/speed_units.txt): a
# plain `while` stays top-tested only from -O3 up, and a whole-file compile of
# the RenderWare sources fingerprints 360 byte-exact functions at -O4,p against
# 259 at -O3 and 130 at -O2 (build/rw_fid.py). The level replaces the default
# -O2; `,p` is still applied per unit.
# `-inline auto`: retail inlines small same-unit callees (batkbin.c
# _rwPluginRegistryWriteDataChunks carries _rwPluginRegistryGetSize inline
# while the out-of-line copy is also emitted; plain -O2 keeps the call).
# `-DRWBUILDNUMBER=55`: the tree defaults to build 101, retail's chunk headers
# are written with build 55 (the `addiu $t0, 0x37` before every
# _rwStreamWriteVersionedChunkHeader call).
cw3.0.1b119 -O4 -inline auto -DRWBUILDNUMBER=55 -nosyspath -Iinclude/rw/std -Iinclude/rw/ps2 -Iinclude/rw/plcore -Iinclude/rw/core -Iinclude/rw/p2 -Iinclude/rw/drvcommon -Iinclude/rw/drvnull -Iinclude/rw/world -Iinclude/rw/worldp2 -Iinclude/rw/p2null -Iinclude/rw/worldp2null -Iinclude/rw/inc

# The ee-gcc 2.96 vendor units (config/gcc_units.txt). CRI shipped its PS2
# middleware as GCC-built libraries - `libadxe.a`'s objects carry
# `gcc2_compiled.` and `__gnu_compiled_c`, and no MWCCPS2 build on disk
# reproduces their size at any optimisation level - so the reconstructed
# sources under src/cri/libadxe compile with the same toolchain the tree
# already pins for the other vendor units. Only the `-I` entries are used;
# tools/eegcc_shim.py pins `-O2 -G0` itself. The layout mirrors the upstream
# decompilation's include root so the vendored files stay verbatim: their
# headers reach each other through `../../../cri/mwlib/...` and reach the CRI
# SDK headers through `../../../recvx-decomp-cri/cri/mwlib/...`, both relative
# to whichever -I directory they are found under.
eegcc296 -Iinclude/rw/std -Iinclude/cri/cri/mwlib/ee -Iinclude/cri/cri/mwlib/ee/lib/libadxe -Iinclude/cri/recvx-decomp-cri/cri/mwlib/include -Iinclude/cri/recvx-decomp-cri/cri/mwlib/ee/include

# The RE4 reconstruction of CRI's library (src/cri/re4) carries its own copies
# of cri_xpt.h, sj.h, sfd.h and friends, and they are NOT interchangeable with
# the RECVX set above: RE4's `Sint32` is `signed long`, four bytes on
# GameCube and eight under this EABI64 target. Its units therefore get their
# own key and their own include root, listed against them in
# config/compiler_units.txt.
eegcc296re4 -Isrc/cri/re4 -Iinclude/rw/std
